How scenarios work

The tools are fixed. The scenarios are data.

An MCP tool description is static metadata, fixed when the server definition deploys. Scenarios are records you create at any time, so a tool can never describe, in its own definition, which scenarios exist.

So the relationship inverts: the org publishes its catalogue outward, and the model does the structuring. Adding a scenario never changes an MCP definition, never requires a deploy, and never requires the client to refresh tools.

Three tools

  • discover — returns the shortlisted catalogue with parameters, legal values and your example prompts.
  • run — resolves to records and returns a reviewable list. Only with confirmation does it generate.
  • check — polls a run, then returns the finished documents.

Two tiers of selection

Most scenarios are an object, a filter, a template and a field mapping — no code. A few cannot be expressed as a WHERE clause: “accounts with no signed NDA in twelve months” is an anti-join against generated documents. Those name an Apex class.

A resolver returns ids only. Display stays declarative, so presentation can change later without breaking a single resolver in the field.

What stays out

A scenario stops at selection. What happens to each document once it exists — email it, e-sign it, combine it — is already an S-Docs document action. A scenario points at one; it does not grow a parallel delivery path.
